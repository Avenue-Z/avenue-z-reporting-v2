## 3. F3: never lock a blank account-level number

### 3.1 What happened (evidence: the private QA log and lock readout)

- One client's locked August tiles answer, captured on the first view of that tab, holds
  `NET_NEW_FOLLOWERS` with `value: null` and `context: null`. The other requested metrics have values.
- An independent Dash call for the same request minutes later returned a real value and prior value.
- That client's follower graph did not lock at that moment, and was captured correctly on a later
  view. That fits a short Dash blip on that metric: the graph's rule (`ALL_CHANNELS` present) held it
  back, and the tiles' rule did not.

### 3.2 Why the code let it through

- `completeReportsData` (`lib/organic-social/locking-client.ts:22-41`) decides whether an answer may
  be locked. For a tiles answer it checks only that the brand entry exists and every requested
  metric **key** is present (`:34-40`). A metric with `value: null` passes.
- The builder turns the null into 0 (`lib/organic-social/outline-headlines.ts:35`) with no
  comparison, and a locked row is served for good (`locking-client.ts:73-75`).
- It also reaches the next month. When September locks, its comparison is replaced at read time by
  August's locked value (`locking-client.ts:95-99`, `withLockedBaseline` `:48-58`). While August
  holds the null, September's comparison for that tile would be blank too. Once August is fixed
  (§3.6), September picks up the corrected value on its own.

### 3.3 The rule, and exactly what the evidence covers

A blanket "any null is incomplete" would be wrong: a quiet period legitimately returns nulls for
post-level metrics.
- The 2026-09-22 probe (private `probes/outline-brand-entry-shape-2026-09-22.out`) found one-day
  windows with no posts come back with most metrics null and a few numbers.
- Three read-only probes on 2026-09-24 used the tiles' request shape (TOTAL_GROUPED_METRIC,
  aggregate_by=BRAND, require_posts=true, Eastern-midnight dates), over every channel tab of the
  October clients, 8 one-day windows per tab, many with no posts. Private files:
  - `probes/f3-null-pattern-2026-09-24.out`: values, without prior dates
  - `probes/f3-null-pattern-ctx-2026-09-24.out`: with prior dates, as the tiles send them
  - `probes/f3-null-pattern-ctx4-2026-09-24.out`: with prior dates, checking value and prior for
    all four metrics below
- What they showed:
  - Every post-level metric was null on the no-post days.
  - **Four account-level metrics were never null, value or prior, on any probed day, on every
    channel that requests them:** `TOTAL_FOLLOWERS`, `NET_NEW_FOLLOWERS`, `PROFILE_VIEWS`
    (Instagram, TikTok) and `PAGE_VIEWS_ALL_POSTS` (LinkedIn).
- The QA's 22 full-month and month-to-date checker runs had no null anywhere (private `dash-audit/`).

**What the evidence does not cover:** X; an account's first days in Dash; a channel in a client's
allowlist that has no account in Dash. The 2026-09-22 probe shows windows before an account's Dash
history, and channels with no account, come back all null.

**The rule:** a reports-data answer (not GRAPH, not MULTI_METRIC_MEDIA_TYPE) is incomplete if it
requested any of those four account-level metrics and one came back with a null value (the entry
null, or its `value` null). It is then served, not stored, and asked for again on the next view.
- It catches the observed failure.
- It cannot stop a quiet month from locking inside the evidence's scope: account-level metrics
  stay numbers when nothing is posted.
- **It changes one earlier decision on purpose.** An all-null tiles answer used to count as complete
  (CLAUDE.md, "Known Follow-ups: Organic Social locked months", path 2, `:892-897`), on the premise
  that a quiet month looks all-null. The probes show it does not. For a connected account an
  all-null answer is a blank, and it no longer locks.

**Where a null could be real** (outside that scope): an X account, a first month that starts on an
account's first day in Dash, or an allowlisted channel with no account.
- The month would never lock and stays live, which fails safe: live numbers, never a stored wrong
  one.
- Each view re-reads it through the uncached capture client (`locking-client.ts:83`), including the
  YTD block's per-month fan-out (`components/report-sections/organic-social/parts/ytd-review.tsx:30`).
- The hourly lock sweep does the same for the two newest settled months
  (`lib/organic-social/lock-sweep.ts:18-19`, route `app/api/lock-sweep/route.ts:34`, scheduled at
  `vercel.json:13`).
- The warning line repeats each time.
- §7 adds a read-only switch-on check so this cannot happen unnoticed for a future client.

### 3.4 The change

1. **`lib/organic-social/locking-client.ts`:** the constant, placed directly above
   `completeReportsData`'s doc comment (after `type Deps`, `:18`):

   ```ts
   /** Account-level metrics: Dash reports them every day for a connected account, whether or not
    *  anything was posted. Probed 2026-09-24 in the tiles' request shape, with and without
    *  prior-period dates, on every channel tab of the October clients, including many days with no
    *  posts: none of these was ever null, value or prior, on a channel that requests it, while every
    *  post-level metric was null on the no-post days. So a null here is a transient blank from
    *  Dash, not a quiet month, and locking it would show a wrong number for good (it happened on
    *  staging: a follower tile locked as 0). */
   ```

   and in `completeReportsData`, the last line (`:40`) is replaced with:

   ```ts
     if (!brand.metrics || !p.metrics.every((k) => k in brand.metrics!)) return false
     // A requested account-level metric without a value is a transient blank (see ACCOUNT_METRICS).
     return p.metrics.every((k) => !ACCOUNT_METRICS.includes(k)
       || (brand.metrics![k] as { value?: unknown } | null | undefined)?.value != null)
   ```

### 3.6 The staging remedy (separate from the PR; my written go; after all three PRs reach staging)

The guard stops future blanks. It doesn't remove the one already stored.

1. **Order.** All three PRs reach staging first, so the recapture runs through the guarded code and
   the check sees F2's arrow as well.
2. **Read-only pre-scan.**

     `jsonb_path_exists(response, '$.data.*.metrics.<METRIC> ? (@ == null || @.value == null)'::jsonpath)`.

     - On literal JSON it matches a bare null entry and a null value, and matches neither a real

       `probes/f3-remedy-literal-and-lock-audit-2026-09-24.out`).

       `probes/f3-remedy-match-v3-2026-09-24.out`).

     month stops the remedy.
3. **The delete.** A private, host-guarded script (staging endpoint only), dry-run by default. The
   client slug and the month's last day (`YYYY-MM-DD`, how `period_end` is stored) are literals in
   the private script only. One batch transaction:
   - `WITH d AS (DELETE FROM dash_response_locks WHERE client_id = (SELECT id FROM clients WHERE slug
     = $slug) AND period_end = $lastDay::date AND jsonb_path_exists(response,
     '$.data.*.metrics.NET_NEW_FOLLOWERS ? (@ == null || @.value == null)'::jsonpath) RETURNING 1)
     SELECT 1 / (CASE WHEN count(*) = 1 THEN 1 ELSE 0 END) FROM d`
     - It fails, and so rolls back, unless exactly one row was deleted.
     - The table is keyed on `client_id`, not slug (`lib/db/schema.ts:422-431`).
   - A second statement that divides by zero unless Renaissance's row md5 is unchanged (the pattern
     the switch-on script used on 2026-09-24).
4. **Recapture.** Re-view that tab. The page shows Dash's value with its comparison, and a read-only
   probe shows the new row holds a real value. Expected along the way:
   - a `late lock` warning (`locking-client.ts:93`), because the month's lock day has passed
   - the new tiles row is captured later than that month's other rows, so a follower figure can
     differ slightly from the graph captured earlier
5. **Verify the escape.** This also runs, for the first time, the manual escape CLAUDE.md records as
   unverified ("delete that client's rows for the month ... then let the next render ... capture it

## 4. F1: a post that tags the client is never an owned post

## 5. F2: the arrow follows the direction of change, not the sign of last period

### 5.1 What happened

On a live month, a tile's prior value was negative and its current value positive, and the tile read
as a red "down" arrow.

### 5.2 Why the code does it

- `delta()` (`lib/organic-social/headline-build.ts:12-18`) returns `((cur - prev) / prev) * 100`, so
  a negative `prev` flips the sign.
- The card draws the arrow and color from the sign (`components/charts/kpi-card.tsx:61-71`).
- Callers:
  - the outline tiles, `lib/organic-social/outline-headlines.ts:41`
  - the outline media row, `lib/organic-social/outline-media.ts:29,34`
  - Renaissance's tiles, `headline-build.ts:61`

### 5.3 The change

1. **New file `lib/organic-social/outline-delta.ts`:**
   ```ts
   import type { TotalMetric } from '@/lib/dash-social/types'

   /** Prior-period percent change for the outline tiles, measured against the size of the prior
    *  value, so the arrow always shows the direction of change. The shared delta()
    *  (headline-build.ts) divides by the signed prior: when last period was negative (Net New
    *  Followers can be) its sign flips, so -2 to +4 reads as a red "down 300%". That one is left as
    *  it is because Renaissance's tiles read it. No prior, or a prior of 0, is no comparison,
    *  exactly as delta(). */
   export function outlineDelta(m: TotalMetric | undefined): number | undefined {
     if (!m) return undefined
     const cur = m.value ?? 0
     const prev = m.context
     if (prev == null || prev === 0) return undefined
     return ((cur - prev) / Math.abs(prev)) * 100
   }
   ```
2. **`outline-headlines.ts`:**
   - `:8` imports `outlineDelta` in place of `delta`, and `:41` uses it.
   - The header (`:1-4`) is reworded in place: it no longer says the tiles are built "by the same
     rules as buildPlatformHeadline", and names this one difference.
3. **`outline-media.ts`:** `:6` imports it, and `:29` and `:34` use it.

**What stays on the signed `delta()`:**
- **Renaissance:** `headline-build.ts` is not edited; `buildPlatformHeadline` (`:61`) keeps it.

  (`components/report-sections/organic-social/parts/outline-data.tsx:42-43`). None of the October
  clients reaches them.
- **The other `delta` functions in the repo** are separate local functions in other reports, not
  touched: `lib/meta/kpis.ts:8`, `lib/linkedin/kpis.ts:8`, `lib/paid-search/kpis.ts:9`,
  `lib/gsc/client.ts:91` and six components.

**Unaffected:**
- **The breakdown:** the engagement breakdown reads `getOutlineKpis`, so it follows.
- **YTD:** it reads values only (`lib/organic-social/ytd.ts:66-72`).
